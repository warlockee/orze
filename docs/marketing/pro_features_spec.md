# Orze Pro — Feature Specification

## Overview

Orze Pro extends the open-source orchestrator with team collaboration, analytics, and operational features that research labs need when running experiments at scale. The free tier remains fully functional — Pro adds visibility, insights, and support.

---

## Feature 1: Team Dashboard

### Problem
The current admin UI (`orze --admin`) binds to localhost. In a lab setting, researchers want to check experiment status from their laptops without SSH-ing into the GPU machine.

### Solution
Network-accessible dashboard with authentication.

### Spec
- **Auth**: Token-based (generated with `orze pro token create`). No external auth provider needed for Pro tier.
- **Binding**: `orze --admin --host 0.0.0.0 --port 8787` with `--auth-token` flag
- **Views**:
  - **Cluster Overview**: all nodes, GPU status, active experiments per GPU
  - **Experiment Feed**: real-time stream of completed/failed/running experiments
  - **Leaderboard**: sortable, filterable, with metric history charts
  - **Queue**: pending experiments with estimated wait time
  - **Logs**: per-experiment log viewer (stream from `results/{id}/`)
- **Tech**: extend existing FastAPI admin server, add token middleware, serve on all interfaces
- **Implementation effort**: ~3 days (auth + network binding + log viewer)

### MVP
Token auth + network binding + log viewer. Charts can come later.

## Feature 2: GPU Utilization Analytics

### Problem
Labs don't know how efficiently they're using their GPUs. "Are we GPU-bound or idea-bound?" is unanswerable without data.

### Spec
- **Collection**: every heartbeat (default 30 min), record per-GPU status (training/eval/idle) to `results/_analytics.db` (SQLite)
- **Metrics**:
  - GPU utilization % (training+eval time / wall time) — daily, weekly, all-time
  - Idle time breakdown: no ideas queued vs. cooldown vs. disk full vs. failed
  - Experiments per GPU per day
  - Average training time per experiment (trend over time)
  - Cost attribution: GPU-hours per idea (requires user-provided $/GPU-hour config)
- **Reports**:
  - `orze pro report` — CLI command, prints summary to terminal
  - Weekly email/Telegram digest (opt-in via notifications config)
  - JSON export for custom dashboards
- **Dashboard integration**: utilization chart on Team Dashboard
- **Implementation effort**: ~4 days (collection + aggregation + CLI report + dashboard chart)

### MVP
Collection + CLI report. Dashboard chart and email digest are follow-ups.

### Config
```yaml
pro:
  analytics:
    enabled: true
    cost_per_gpu_hour: 2.50  # optional, for cost attribution
    weekly_digest: true
    digest_channel: telegram  # or slack, email
```

## Feature 3: Experiment Trend Analysis

### Problem
After 200+ experiments, it's hard to see the forest for the trees. Is the leaderboard still improving? Are we exploring diminishing returns? Which hyperparameters actually matter?

### Spec
- **Convergence Detection**: track best metric over time, flag when improvement rate drops below threshold
  - "Your best score hasn't improved in 50 experiments. Consider changing your search strategy."
- **Hyperparameter Importance**: simple correlation analysis between config values and metrics
  - "Experiments with `learning_rate < 1e-4` score 12% higher on average"
  - Uses completed experiments from idea_lake.db
- **Cluster Analysis**: group similar experiments, identify which design choices drive results
  - "Backbone choice explains 60% of variance. Augmentation type explains 15%."
- **Output**: Markdown report saved to `results/_trend_analysis.md`, optionally sent as notification
- **Trigger**: automatic after every N completions (configurable, default 50), or `orze pro trends`
- **Implementation effort**: ~5 days (convergence is easy, HP importance is moderate, cluster analysis is the stretch goal)

### MVP
Convergence detection + HP importance ranking. Cluster analysis is v2.

### Config
```yaml
pro:
  trends:
    enabled: true
    interval: 50  # analyze every N completions
    notify: true  # send report via notifications
```

## Feature 4: Advanced Retrospection Reports

### Problem
The built-in retrospection feeds context to research agents, but doesn't produce a human-readable summary. Lab leads want a weekly "state of research" update.

### Spec
- **Weekly Summary** (generated by LLM agent):
  - Top 5 experiments this week with key insights
  - What design choices drove improvements
  - What was tried and didn't work (and why)
  - Recommended next directions
  - GPU utilization summary
- **Delivery**: Markdown file + optional notification (Telegram/Slack/email)
- **Customizable**: users can configure which metrics to highlight, which experiments to focus on
- **LLM Backend**: uses the same research agent backend (Gemini/OpenAI/etc.) already configured
- **Implementation effort**: ~2 days (template + LLM call + scheduling)

### Config
```yaml
pro:
  weekly_report:
    enabled: true
    day: monday  # or sunday, friday
    time: "09:00"
    backend: gemini  # reuse research agent config
    notify: true
```

## Feature 5: Cloud Templates

### Problem
Setting up Orze on cloud GPU instances requires manual configuration — installing CUDA drivers, mounting shared storage, configuring networking between nodes.

### Spec
- **Templates provided as**:
  - Shell scripts (`setup_aws.sh`, `setup_gcp.sh`, `setup_lambda.sh`)
  - Docker images (`orze/orze-pro:latest` with CUDA, PyTorch, common ML deps)
  - Terraform modules (for multi-node setups)
- **Cloud providers**:
  - AWS: EC2 with EFS/FSx, ParallelCluster template
  - GCP: Compute Engine with Filestore
  - Lambda Labs: multi-GPU instance setup
  - RunPod: serverless GPU template
  - Vast.ai: template for rented GPUs
- **Features**:
  - Auto-mount shared filesystem
  - Auto-start Orze on boot
  - Pre-configured watchdog service
  - Spot/preemptible instance support (checkpoint + resume)
- **Implementation effort**: ~5 days (scripts are straightforward, Terraform takes longer, Docker is ~1 day)

### MVP
AWS (EC2 + FSx) and Lambda Labs shell scripts + Docker image.

## Feature 6: Priority Support

### Spec
- **Channel**: dedicated email (pro-support@orze.ai)
- **SLA**: 24-hour response time during business days
- **Scope**: configuration help, bug triage, integration guidance
- **Exclusions**: custom development, training script debugging
- **Tooling**: use a simple shared inbox (Fastmail, Hey, or similar). Don't over-invest in ticketing until there are 50+ Pro customers.

## Licensing & Delivery

### How Pro features are gated
- **License key**: `orze pro activate <key>` stores key in `~/.orze/license.json`
- **Validation**: offline-first. Key contains expiry date + feature flags, signed with Ed25519. No phone-home required (researchers hate that).
- **Grace period**: 7 days after expiry before features deactivate
- **CLI**: `orze pro status` shows license info, active features, expiry

### Why offline-first
Research labs often run on air-gapped clusters or behind strict firewalls. License validation that requires internet access is a dealbreaker. The key is self-contained — signed JSON with expiry, verified locally.

```python
# License key structure (base64-encoded, signed)
{
    "customer": "MIT CSAIL",
    "email": "researcher@mit.edu",
    "plan": "pro",
    "features": ["dashboard", "analytics", "trends", "retrospection", "templates"],
    "expires": "2027-03-22",
    "max_nodes": 10,
    "signature": "..."
}
```

## Enterprise Features (Future — Not in Pro)

These are explicitly excluded from Pro to preserve Enterprise upsell:

- **SSO/RBAC**: SAML, OIDC, role-based permissions
- **Audit logging**: full experiment provenance, config snapshots
- **PostgreSQL backend**: for high-concurrency multi-writer setups
- **Multi-cluster management**: unified view across separate projects
- **Custom research agent skills**: domain-specific agent development
- **Dedicated Slack support**: direct channel with Orze team
- **1:1 onboarding**: setup and integration session
- **SLA**: contractual uptime guarantees
